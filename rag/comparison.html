1. RAG vs Long Context ？

1.1 Long Context 的局限

  1. 效果：Effective Context 可能显著短于 Claimed Context。 模型支持较长的上下文窗口，不代表它能同样有效地利用其中的所有信息。随着上下文变长，部分任务的准确率可能下降。

    长上下文模型的典型问题：

[1] Positional bias - 模型通常更容易利用位于输入开头或结尾的信息，而对位于中间的信息利用较差，呈现近似 U 形的性能曲线

[2] Attention-sink collapse - 长序列中的部分 token 可能获得异常集中的注意力权重，影响模型对其他信息的关注

[3] MLA distortion - Multi-head Latent Attention 通过低维潜在向量压缩并缓存 KV 降低 KV Cache 开销，可能导致在长序列失真

[4] Multi-fact integration failure - 模型能够分别检索到多个相关事实，却无法正确整合它们之间的关系并得出结论

[5] Context interference / Noise sensitivity - 上下文中的噪声、冗余或矛盾内容干扰模型对关键证据的识别与使用

[6] Long-range dependency failure - 模型可能难以稳定关联分散在长文本不同位置的信息

[7] Context dilution - 随着上下文扩张，重要指令或证据的相对显著性下降

  2. 成本：若每次查询都将全部资料作为上下文输入，输入 Token 成本和 Prefill 延迟会随输入规模增加。相比之下，RAG 可以先检索少量相关片段，减少每次请求需要处理的输入量。

1.2 各维度对比

维度Long ContextRAG
工程复杂度低高，需要切块、索引、检索、排序等整套链路
输入成本高，资料越长通常需要处理的输入 token 越多较低，通常只将检索到的相关内容送入模型减少输入 token
延迟高，长输入通常增加 Prefill 开销需要额外的检索与排序步骤，但通过减少输入 token降低生成阶段的开销；结合 ANN 等索引技术，可支持大规模语料下的高效检索

长文档推理质量适合整体阅读、总结及跨段落整合；上下文变长时，信息利用效果可能下降适合定位相关证据；跨文档整合、全局总结等任务可能需要多轮检索或额外的层级化处理

1.3 选型建议

场景初步选择
小规模资料、低频查询、快速原型Long Context
大规模知识库、高频事实查询RAG
全局综述、跨大量资料归纳Long Context、分层摘要或 GraphRAG 等
法律、研究等高准确性要求场景根据证据覆盖、可追溯性和评测结果选择

两者并非相互替代，而是互补关系。Long Context 提供更大的原始信息容纳能力，RAG 不仅能够缓解上下文窗口与输入成本的限制，也通过检索、排序与筛选提供更相关的上下文。高质量的检索结果能够提高输入的信号噪声比，让模型更有效地利用上下文。二者协同演进。

2. RAG vs Grep ？

2.1 什么时候 Grep 更合适？

当需要查找的是精确对象时，优先考虑 Grep 或关键词搜索，而不是直接使用向量检索。

典型场景：

  • 代码、函数名、变量名
  • 配置、错误码、日志
  • 文件名、路径和精确字符串

这些对象通常具有明确的文本标识，精确字符串匹配更可靠。

2.2 Grep 与语义检索的边界

方式适合的问题局限
Grep / 精确搜索函数名、错误码、配置项、路径难以处理同义表达和概念性问题
BM25 / 关键词检索根据词项匹配寻找相关文档对语义表达差异的适应能力有限
向量检索根据自然语言描述寻找语义相关内容不保证精确标识符和细节匹配
混合检索同时需要关键词匹配与语义召回需要融合与排序机制

语义索引是否值得引入，取决于查询类型、搜索效率、语料规模和维护成本。

例如：

  • 查询精确函数定义：Grep 通常更直接。
  • 查询“项目里是如何处理模型检查点恢复的”：语义检索可能更有价值。
  • 大型代码库中的概念性查询：可以结合关键词检索、语义检索和代码结构信息。

边界在哪？对于 MB 级的本地代码仓库，直接搜索往往已经足够，预先建立语义索引不一定值得其构建、同步和维护成本。仓库到 GB 级、跨多个仓库、用户经常问哪里实现了 XX 这个概念，而不是这个函数在哪，语义索引就重新有价值了。

2.3 典型场景

  1. 代码搜索 + Agent 迭代：Grep 可以作为 Agent 的搜索工具，结合读取文件、运行测试和后续搜索形成循环。

  2. 企业级多模态资料：可以考虑 Multimodal RAG，也可以组合使用 OCR、结构化解析、关键词检索和向量检索等技术。

  3. 跨章节硬件文档：如果文档规模较小且需要保留完整上下文，可以直接提供相关文件；资料规模较大时，也可以使用检索定位证据。

3. RAG → Graph RAG ？

3.1 为什么需要 GraphRAG？

典型问题：

  • 这个功能过去两年改过几次，每次为什么改？
  • 这份需求涉及哪些上下游系统？
  • 多份设计文档之间互相存在哪些关联和矛盾？
  • 大量文档整体上讨论了哪些主题？

这些问题的证据可能分散在评审记录、周报和设计文档之间。普通向量检索可以找回语义相关的文本片段，但不一定能直接表示实体之间的关系，也不一定能完整覆盖全局主题。

3.2 主要方案

GraphRAG

微软提出的 GraphRAG 方案会从文本中抽取实体与关系，构建图结构，并通过社区划分和摘要等机制支持全局性问题。

它的优势是能够利用跨文档的实体关系和主题结构；代价则包括实体与关系抽取、图构建、摘要生成和索引维护的高成本。

LazyGraphRAG

LazyGraphRAG 尝试减少构建完整图索引所需的前期工作与成本，并将更多工作推迟到查询阶段，索引成本约为完整 GraphRAG 的千分之一。

LightRAG

LightRAG 保留实体关系主线，砍掉最贵的社区摘要，支持增量更新，建索引的成本大约是 GraphRAG 的百分之一。

3.3 选型建议

场景初步选择
具体事实查询、普通企业问答混合检索 + rerank
跨文档实体关系查询知识图谱 + RAG 或 GraphRAG
大量资料的全局主题归纳GraphRAG、LazyGraphRAG 等
希望兼顾实体关系、检索和增量更新可评估 LightRAG 等方案

工程建议： 上图之前，先确认问题是否真的需要显式关系结构。很多企业问答仍然可以通过混合检索与 rerank 解决；当任务需要跨文档推理或全局综述时，再 LazyGraphRAG 或 LightRAG 起步，不要开始就上完整版 GraphRAG。

4. RAG vs Agent Memory ？

4.1 Memory 不等于向量数据库

用户偏好、项目约定、历史决策等信息经常被存入向量库，并被统称为长期记忆，但这并不意味着向量检索本身就构成了完整的 Memory 系统。

经典 RAG 是无状态查询，关注如何根据当前查询检索相关资料；

Memory 系统需要的是有写策略、有更新策略的外部状态：

  • 写入策略：什么信息值得保留？
  • 更新策略：信息发生变化后如何更新？
  • 失效策略：什么信息已经过期？
  • 冲突处理：新旧记忆不一致时如何处理？
  • 读取策略：当前任务需要哪些记忆？

一个只有读取路径、缺少写入和更新策略的系统，可能随着使用时间增长而积累重复、过期或相互矛盾的信息。

4.2 Memory 与 Retrieval 的关系

Memory 和 RAG 不是互斥关系。

Memory 可以采用不同的存储和读取方式：

  • 结构化数据库：保存稳定的用户偏好、配置和状态。
  • 文件或文档：保存项目约定、历史决策和操作记录。
  • 关键词检索或向量检索：从大量历史记忆中找到当前需要的信息。

例如，稳定的用户偏好可以结构化保存并直接读取；大型项目的历史决策则可能需要通过检索来定位。

工程建议： 对个人助手和长期项目 Agent，先设计 Memory 的写入、更新、失效和冲突处理机制，再根据记忆规模与查询需求决定是否使用 RAG 等检索技术。

5. RAG → Agentic RAG？

5.1 核心区别

传统 RAG 通常按照预设流程完成单次查询、检索、排序和生成。

Agentic RAG 则将 RAG各阶段接口 作为 Agent 的 tool，由模型根据当前任务与已获得的证据决定什么时候检索、检索什么、检索方式。

常见实现方式：ReAct 循环 + 多轮检索

5.2 典型场景：查到 A 才知道需要查 B

例如，训练任务失败后，第一轮日志检索只找到 OOM 报错。进一步调查发现，上周有人修改了数据加载配置，导致 batch size 翻倍。这个答案要查完日志、再查配置变更记录、再对时间才能拼出来。

一次性检索可能只能定位到显存不足；Agentic RAG 的做法是当前证据不足以得出结论时，Agent 可以拆分问题、继续查询相关数据源，并整合验证多轮结果。

5.3 最小实现闭环

  1. 将检索封装为可调用的 Tool。
  2. 让模型读取检索结果，并识别尚未解决的问题。
  3. 根据明确的信息缺口决定是否继续检索。
  4. 检查多轮证据是否足以支持最终结论。
  5. 在证据足够时停止；否则继续查询或明确说明不确定性。

5.4 主要代价与风险

1. Token 与延迟增加

多轮检索通常意味着多次工具调用、上下文处理和端到端延迟。FAQ 等简单问题不需要复杂的 Agentic RAG。

2. 查得多不等于答得对

更多检索结果不一定意味着更多有效证据。Agent 可能忽略关键片段、错误整合事实，或者根据不充分的证据作出过度推断。

因此，需要关注的不只是召回数量，还包括证据覆盖、事实一致性、答案可追溯性和停止条件。

6. RAG → Multimodal RAG？

6.1 适用场景

Multimodal RAG 面向文本、图像、表格、音频和视频等多模态资料有跨越式改进，适用于：

  • 工程图纸与技术手册检索。
  • 图文混合文档问答。
  • 视频内容定位与事件检索。
  • 会议录音和音视频资料检索。

6.2 与传统文本 RAG 的区别

多模态检索需要根据资料类型选择不同的处理方式，例如：

  • 文本提取与 OCR。
  • 图像特征提取与图像语义检索。
  • 音频转录与语音内容检索。
  • 视频帧抽取、时间戳定位和片段检索。

系统还需要保留检索结果与原始证据之间的对应关系，例如页码、图像区域、时间戳和视频片段。

6.3 主要挑战

  • 跨模态语义对齐。
  • 图像、表格和视频中的细粒度信息定位。
  • 时序关系与上下文保留。
  • 检索结果与原始证据的关联。
  • 多模态索引的构建、更新与维护成本。

并非所有多模态任务都需要统一的多模态向量索引。具体方案取决于资料类型、查询方式和精度要求。

7. 总结

核心原则： 不要从“我要使用哪种技术”开始，而应从“当前问题缺少什么信息、需要什么能力”开始。先选择能够解决问题的最简单方案，再根据召回质量、推理需求、成本和维护复杂度决定是否引入更复杂的系统。
