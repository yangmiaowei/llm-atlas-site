1. Retrieval 检索层评估

调 chunking / embedding / hybrid / reranker — 看的就是这组指标。

Metrics 评估指标

指标典型评估对象主要回答的问题
Recall@k文档或 chunk相关证据找回了多少？
Precision@k文档或 chunk返回结果中相关内容占多少？
Hit Rate@k查询集合有多少查询至少命中一个相关结果？
MRR排名列表第一个相关结果排得如何？
MAP排名列表与查询集合多个相关结果的排序表现如何？
NDCG@k排名列表分级相关性结果的整体排序如何？

Recall@k（召回率）

检索结果是否覆盖了答案需要的所有信息。

定义： 所有相关的 chunk 中，有多少被检索回来了。

公式： Recall@k=总相关 chunk 数Top-k 中相关 chunk 数​

优化方向：

  • 增大 top-k（但会降低准确率，需要平衡）
  • 使用混合检索（关键词+向量互补）
  • 优化查询改写（query rewriting）
  • 增加多轮检索（先检索再根据结果扩展查询再检索）

注意： 很多人为了提升召回率，把top-k设得很大（比如20或30），结果准确率暴跌，上下文噪音太多，最终答案效果反而更差。召回率和准确率需要 trade-off，不是召回率越高越好。

召回不到排查顺序：

  1. 文档是否正确解析、切片并写入索引？
  2. Query 是否需要改写、拆分或补充关键词？
  3. Embedding 模型是否适合当前领域和语言？
  4. Metadata Filter 是否过严，或者过滤条件是否错误？
  5. ANN 参数是否导致候选遗漏？
  6. 是否需要增加 BM25、多路召回或其他检索通道？

Precision@k（精确率）

检索结果里有多少是对的。

用来判断噪音多不多。 但它有个明显特点：对 chunk 切分方式非常敏感，chunk 切得粗细，结果差别很大。

定义： 检索返回的 Top-k 个 chunk 中，有多少是真正和查询相关的。

公式：Precision@k=kTop-k 中相关 chunk 数​

优化方向：

  • 调整embedding模型（换更强的embedding）
  • 优化分块策略（chunk 大小、重叠度）
  • 增加重排序（rerank）环节
  • 调整top-k数量

注意： 很多人只看top-1的准确率，但实际RAG用的是top-5或top-10。top-1准确率高不代表top-10 准确率也高——可能第一个很准，但后面九个都是噪音。

Hit Rate@k（命中率）

衡量Top-k 至少命中一个相关chunk的查询的比例。

前 k 个结果里，只要有一个是对的，就算成功。 只关心 “找到”或“没找到”，是一个二元（0或1）指标。

它常用于做非常粗粒度的可用性判断。 缺点：信息量太粗，几乎看不出质量差异。

定义：指在召回的 Top-K 个结果中，是否包含了正确的答案文本块。

公式：HitRate@k=查询总数至少命中一个相关结果的查询数​

示例：100 次查询中，92 次至少命中一个相关 chunk，Hit Rate@k 就是 92%。

解读：命中率高，说明召回系统下限很高，大部分情况下都能把相关的基本信息捞出来。 对于需要多个证据共同支持答案的 RAG 任务，Hit Rate 高不一定意味着证据足够完整。

MRR ( Mean Reciprocal Rank )（平均倒数排名）

第一个相关 chunk 排第几。

适合用来评估排序模型。 缺点：只看第一个命中，后面的全当不存在。

定义：衡量每个查询的第一个相关chunk出现在检索结果中排名的倒数，再对所有查询求平均。这个指标不仅关心是否命中，还关心正确答案命中的位置。

对于单次查询，如果正确答案排在第 n 位，其分值为 1/n ；如果未命中，则分值为 0。 MRR 是所有查询分值的平均值。

公式：MRR=∣Q∣1​∑i=1∣Q∣​ranki​1​

其中，∣Q∣为查询总数；ranki​为第 i 个查询中第一个相关 chunk 的排名。

示例：

查询1：正确答案排第 2，得分 1/2。

查询2：正确答案排第 1，得分 1/1。

查询3：正确答案排第 5，得分 1/5。

MRR = (0.5 + 1 + 0.2) / 3 = 0.567。

解读：MRR 值越接近 1，说明系统越倾向于将最相关的结果排在最前面，这对于只取 Top-1 结果的场景尤为重要。

MAP ( Mean Average Precision )（平均准确率均值）

多个相关 chunk 的排序表现。

对于每个查询，先计算 Average Precision（AP），再对所有查询取平均。

MAP 通常基于二元相关性标注；如果相关性有多个等级，NDCG 往往更自然。

NDCG@k ( Normalized Discounted Cumulative Gain ) （归一化折损累计增益）

考虑相关程度后，整体排序是否合理。

  • Gain（增益）：一个检索结果有多相关，相关性越高，贡献越大。
  • Discounted（折损）：排名越靠后，结果对总得分的贡献越小。
  • Normalized（归一化）：将实际排序的得分与理想排序的得分比较，使结果通常落在 0 到 1 之间。

考虑相关性等级和结果位置，对高排名的高相关性结果给予更大权重。

适合评估相关性具有多个等级、且排序位置很重要的检索任务。

指标关注什么是否考虑多个相关结果相关性
MRR只看第一个相关结果否，只看第一个相关结果二元相关性
MAP关注所有相关结果，并综合考虑它们各自出现时的检索精确率是，考虑多个相关结果二元相关性
NDCG可以进一步利用不同等级的相关性标签，衡量整个排序的质量是，综合评估多个结果的排序分级相关性

Context Relevance（上下文相关性）

定义： 经过重排序和裁剪后最终喂给大模型的上下文，和用户 query 的相关程度。

计算方法：LLM-as-judge

优化方向：

  • 增加重排序环节，把最相关的排前面
  • 优化上下文组装策略（只取每个文档最相关的段落）
  • 增加上下文压缩（用大模型提炼关键信息）
  • 调整上下文窗口大小

评估方法与工具

  • 人工标注基准集： 构建包含（查询， 相关文档列表）的黄金测试集。
  • 自动化评估脚本： 使用如RAGAS、TruLens等框架的检索评估模块。
  • A/B测试： 在生产环境中对比不同检索器的效果。
# 示例：使用RAGAS计算检索指标
from ragas.metrics import (
    context_precision,
    context_recall,
    faithfulness
)
from ragas import evaluate

# dataset 需包含 questions, contexts, answer, ground_truth 等字段
results = evaluate(
    dataset=eval_dataset,
    metrics=[
        context_precision,
        context_recall,
    ]
)
print(results)

2. Generation 生成层评估

Metrics 评估指标

调 prompt / 换 LLM / 调温度 — 看的就是这组指标。

Faithfulness（忠实度）

定义：答案的每个 claim 是否都能在检索内容里找到依据。

如果相关文档已经被召回，但模型编造了文档中不存在的细节，这是忠实度问题。

生成内容本身是否包含不忠于检索的幻觉(hallucination)

示例：模型声称“XR-2048 的功耗是 150W”，但检索到的所有文档中仅提及“这是一台低功耗设备”。此处 150W 属于典型的无凭据捏造（Fabrication）。

评估方法：

  • 人工检查。
  • LLM-as-a-Judge。
  • 将答案拆分为原子化陈述（claims），逐条检查证据支持情况。

优化方向：

  • 在 Prompt 中明确要求基于上下文作答，证据不足时明确说明。
  • 提高检索质量，减少无关或相互冲突的上下文。
  • 要求关键结论附带可核验的引用。
  • 必要时增加生成后的事实核验环节。

注意：Faithfulness 关注的是答案与上下文的一致性，并不等同于客观事实正确性。上下文本身也可能存在错误。

Answer Relevance（相关性）

定义：生成的答案是否切合用户问题，是否回应了用户的实际意图。

如果答案中的每句话都有上下文依据，但没有真正回答用户的问题，则属于相关性问题。

例如，用户询问“RAG 和微调有什么区别”，模型只介绍了 RAG 的工作原理，没有解释微调及两者的差异。

评估方法：

  • 人工判断。
  • LLM-as-a-Judge。
  • 在特定评估框架中，也可以通过生成反向问题等方式衡量答案与原问题的关联程度。

优化方向：

  • 明确用户意图和问题中的关键约束。
  • 优化 Prompt，要求优先回答核心问题。
  • 对复杂问题进行意图识别、问题拆解或多轮澄清。
  • 避免无关的背景扩展。

注意：Answer Relevance 不等同于 Answer Correctness。答案可以很切题，但内容仍然错误。

Coherence（连贯性）

定义： 答案内部的逻辑是否连贯，表达是否清晰，前后是否矛盾。

评估方法：

  • 人工评分。
  • LLM-as-a-Judge。

优化方向：

  • 优化答案结构和输出格式。
  • 对复杂答案采用分点组织或分阶段生成。
  • 检查并消除重复、矛盾及不必要的内容。

Hallucination Rate（幻觉率）

定义： 生成的答案中，有多少内容是上下文里没有的、是大模型自己”编”出来的。

计算公式： 幻觉率 = 存在幻觉的答案数 / 总答案数 × 100%

或者更细粒度： Plaintext 幻觉率 = 幻觉内容字数 / 答案总字数 × 100%

评估方法：

  • 人工标注。
  • LLM-as-a-Judge。
  • 专门的事实核验或幻觉检测模型。

优化方向：

  • 强化prompt约束（“只能根据上下文回答，不知道就说不知道”）
  • 增加引用溯源（要求答案标注信息来源）
  • 降低上下文噪音（提升检索准确率）
  • 增加幻觉检测后置环节（生成后检测，有幻觉就重新生成）

基于参考答案的评估

指标描述适用场景
BLEU, ROUGE通过n-gram重叠度衡量生成文本与参考文本的相似性。摘要、翻译等任务，对事实准确性要求相对宽松。
BERTScore利用BERT嵌入的余弦相似度评估语义一致性，更符合人类判断。需要语义对齐的问答和内容生成。
METEOR考虑同义词和词干，比BLEU更接近人工评估。文本生成任务的辅助评估。

3. End-to-End 端到端评估

LLM-as-a-Judge

Metrics 评估指标

Answer Accuracy（回答准确性）

定义： 大模型最终生成的答案，有多大比例是正确的。 这是最直观、也是最受关注的指标。

评估方法：

  • 人工标注
  • LLM-as-judge
  • 参考答案匹配：和标准答案对比（适合有标准答案的场景）

优化方向：

  • 优化检索质量（基础）
  • 优化prompt工程（明确回答规范）
  • 增加引用约束（要求答案必须基于上下文）
  • 选择更强的大模型

常见坑： 答案准确率高不代表系统好。如果准确率80%，但幻觉率30%，那用户体验依然很差——因 为用户不知道哪个答案是对的、哪个是幻觉的。必须和幻觉率一起看。

Answer Completeness（回答完整性）

定义： 生成的答案是否完整覆盖了用户问题的各个方面。

计算方法： LLM-as-judge

优化方向：

  • 优化prompt（明确要求”全面回答，覆盖各个方面”）
  • 增加检索召回率（确保相关信息都被捞回来）
  • 优化上下文组装（确保关键信息不被截断）
  • 增加多轮生成（先生成草稿，再检查补充）

回答不全可能原因：

  • 相关文档没有被召回。
  • 关键证据在 Top-K 截断时被丢弃。
  • 文档切片破坏了上下文关系。
  • 多跳问题只检索到了部分证据。
  • Reranker 将关键文档排到了后面。
  • 上下文过长或冗余，影响模型使用证据。

4. System 系统评估

Metrics 评估指标

指标主要衡量内容
Latency（延迟）请求处理所需的时间
Throughput（吞吐量）单位时间内处理的请求或 Token 数
Cost（成本）完成请求或任务所需的资源成本
Error Rate（错误率）请求执行失败的比例

Latency（延迟）

定义： 系统从接收用户请求到返回响应所需的时间。对于流式生成，还需要区分首次响应时间与完整响应时间。

RAG系统延迟组成部分： 总延迟 = 检索延迟 + 重排序延迟 + 大模型生成延迟 + 网络延迟

常见指标：

  • TTFT（Time to First Token）： 从请求发出到收到第一个输出 Token 的时间，影响用户感知的响应速度。
  • End-to-End Latency： 从用户提交请求到系统完成整个响应的时间，反映完整请求的处理效率。
  • P50 / P95 / P99 Latency： 分别表示第 50、95、99 百分位的请求延迟，用于衡量典型体验和长尾延迟。

延迟通常受到以下因素影响：

  • 检索、重排序及上下文组装耗时。
  • 大模型推理时间，包括输入处理和输出生成。
  • 多轮检索、工具调用及重复生成。
  • 网络通信、排队等待与并发负载。

优化方向：

  • 优化检索性能（用更快的向量数据库、ANN算法）
  • 减少top-k数量（但会影响召回率，需要平衡）
  • 优化重排序（用更快的rerank模型，或减少重排序的候选数）
  • 大模型流式输出（先返回首token，再逐步生成）
  • 缓存常用查询的结果
  • 对独立的检索或处理任务采用并行执行

注意：很多人为了提升效果，把top-k设得很大、加了重排序、加了多轮检索，结果延迟从1秒变成 5秒。效果提升了10%，但用户流失了30%——得不偿失。延迟和效果必须平衡。

Throughput（吞吐量）

定义： 系统在单位时间内完成的请求或处理的 Token 数量，反映系统的处理能力。

常见衡量方式：

  • Request Throughput： 单位时间内成功完成的请求数，例如 requests/s。
  • Token Throughput： 单位时间内处理或生成的 Token 数，例如 tokens/s。

影响因素：

  • 模型推理能力与 GPU 等计算资源。
  • 并发请求数量及请求长度。
  • 动态批处理、KV Cache 等推理优化机制。
  • 检索服务、数据库及网络等上下游组件的性能。

优化方向：

  • 合理设置并发度与批处理策略。
  • 优化模型推理和检索组件。
  • 使用异步处理，减少不必要的阻塞等待。
  • 根据实际负载进行资源扩缩容。

注意： 吞吐量需要结合并发数、请求复杂度、成功率和延迟分位数一起分析。吞吐量提高不一定意味着单个请求更快，也不代表系统质量更好。

Cost（成本）

定义： 系统完成请求或任务所消耗的计算、模型调用及基础设施资源成本。

常见衡量方式：

  • Cost per Request： 平均每次请求的成本。
  • Cost per Successful Task： 每个成功完成任务的平均成本。
  • Cost per 1,000 Requests： 每千次请求的总成本。

主要成本来源：

  • 大模型输入与输出 Token。
  • Embedding 模型及向量索引构建、更新。
  • Reranker 模型推理。
  • 多轮检索、Agent 工具调用与重复生成。
  • 向量数据库、计算资源、存储和网络服务。

优化方向：

  • 减少冗余上下文和不必要的模型调用。
  • 根据任务难度选择合适的模型。
  • 对高频、可缓存的查询复用结果。
  • 优化检索流程，减少无效候选和重复计算。
  • 在满足质量要求的前提下优化模型、资源和部署配置。

注意： 单次请求成本降低不一定意味着整体效率提高。如果优化导致答案质量下降、重试增加或任务完成率降低，总体成本反而可能上升。因此，应结合回答质量、任务成功率和每个成功任务的成本综合评估。

Error Rate（错误率）

定义： 在指定统计窗口内，执行失败的请求占总请求数的比例。

Error Rate=总请求数失败请求数​×100%

失败类型可以包括：

  • 检索服务或数据库调用失败。
  • 模型 API 超时、限流或返回错误。
  • 工具调用失败、参数校验失败。
  • 请求处理异常或生成流程中断。

优化方向：

  • 增加超时控制、重试策略和异常处理。
  • 对外部服务使用限流、熔断等保护机制。
  • 监控错误类型与发生频率，定位故障组件。
  • 对重试设置次数和退避策略，避免故障时放大负载。

注意： 应区分技术错误与业务失败。例如，模型成功返回一个答非所问的答案，在技术层面可能是成功请求，但在业务层面仍然是失败任务。
